# M30.5 — Attachment content inlining — SPEC (→ 3.0.4)

**Status: approved (user, 2026-07-17 triage: "Inline small text files"),
implemented.**

## The gap (from live desktop testing)

Attaching a file inserts `[Attached file: data/uploads/<name>]` into the
message — a bare path reference. No provider can act on it: API transports
(grok/chatgpt/ollama) have no filesystem at all, and the agentic claude
transport now (correctly, M30.3) runs in a neutral cwd where the relative
path resolves to nothing — it searched, found nothing, and confidently told
the user their upload was broken. "Attach a text file and ask about it" —
the obvious use — never actually worked by design; it only ever *appeared*
to work via the pre-M30.3 cwd accident.

## Change — one helper, both surfaces

`core/chat_turn.py` gains `inline_attachments(text) -> str`, applied to the
NEW user message inside `build_turn_messages()` (the shared assembly seam —
web and CLI get it identically):

- Scans for `[Attached file: <path>]` lines (max 3 per message — prompt-size
  bound).
- Each path is read through **FileManager.read_file** — the allowlist
  governs, exactly as every other read (PermissionError → skip). No new
  filesystem access path.
- **Text files only**, decided by extension allowlist (txt, md, markdown,
  xml, json, yaml, yml, csv, tsv, toml, ini, cfg, log, py, js, ts, sh, html,
  css, sql) — conservative on purpose; images/binaries stay reference-only
  until a vision path exists (Later).
- **Capped at 32 KB** per attachment; over-cap content is truncated with an
  explicit `[...truncated at 32 KB...]` marker so the model knows.
- Injected immediately after the reference line as a fenced block:
  `--- Attached file content: <path> ---` … `--- End of attached file ---`.
- **Best-effort, never fatal**: any failure (missing file, not allowlisted,
  non-text extension, read error) leaves the message byte-identical for that
  reference. Debug-level log only.

**Provider-bound only — records stay raw.** History (`record_turn` uses the
original message), the UI bubble, memory extraction, and exports all keep
the reference form; only the provider-bound `Message` carries content. Past
turns replayed from history are NOT re-inlined (cost bound; the content was
in context when it mattered).

## Tests

- chat_turn units: inline success (content present, reference retained);
  32 KB truncation marker; non-text extension skipped; missing /
  non-allowlisted file leaves message unchanged; >3 references → only first
  3 inlined; messages without references byte-identical (fast path).
- API: `/chat` with an uploaded file — the provider-visible message contains
  the file content; the recorded user turn does NOT.

## Self-review / risks

- The regex is anchored to whole lines in the exact UI-inserted form —
  arbitrary prose mentioning "[Attached file: …]" mid-sentence is not
  matched.
- 3×32 KB worst-case prompt growth (~96 KB ≈ 25k tokens) is deliberate
  headroom below provider context floors; the cap is a named constant.
- CLI parity is free (shared seam) and allowlist-governed — typing a
  reference line by hand inlines the same way, which is a feature.
