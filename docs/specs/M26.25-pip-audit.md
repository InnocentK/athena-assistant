# M26.25 — Dependency vulnerability scanning (pip-audit) + first remediation — SPEC

**Status: specced, awaiting go-ahead. Do NOT implement without explicit approval.**

## Why

M26.19 pinned dependencies to exact versions — great for reproducibility, but
pins go stale and accrue CVEs silently with nothing watching. A scanner turns
"our pins are frozen" into "our pins are frozen *and known-clean*."

## Measured baseline (this session — this is a REAL finding, not hypothetical)

`pip-audit -r requirements.txt --no-deps` against the current pins:

```
Found 4 known vulnerabilities in 1 package
python-multipart 0.0.26  PYSEC-2026-3037  fix: 0.0.30
python-multipart 0.0.26  PYSEC-2026-3036  fix: 0.0.30
python-multipart 0.0.26  PYSEC-2026-3040  fix: 0.0.31
python-multipart 0.0.26  PYSEC-2026-3039  fix: 0.0.27
```

`python-multipart` is a FastAPI form-parsing dependency. All four are fixed by
**bumping to 0.0.31**. This milestone both adds the scanner AND does the first
remediation.

## Scope

1. **Dev dep:** `pip-audit==<pinned>` in `requirements.txt`.
2. **Remediate the known finding:** bump `python-multipart==0.0.26 → ==0.0.31`
   in `requirements.txt`. Then: fresh install, **full gate green** (`task ci`) —
   confirm the bump doesn't break multipart/form handling (Athena uses it via
   FastAPI; exercise any form/upload path in the suite). Re-run `pip-audit` →
   expect **0 vulnerabilities**. Treat any *other* package the audit newly flags
   the same way (assess → bump if safe → re-test).
3. **Taskfile:** `audit` task (`pip-audit -r requirements.txt --no-deps`).
4. **CI (M26.20):** add a `pip-audit` step. Decide failure policy at
   implementation: **recommend non-blocking to start** (`|| true` or
   `--exit-code 0` with the report surfaced) so a newly-disclosed upstream CVE
   doesn't red-wall an unrelated PR overnight — tighten to blocking once the
   team is comfortable triaging. Document the choice.
5. **Version:** bumping `python-multipart` is a real dependency change → **bump
   to 2.6.23** (or whatever the next code version is at implementation order).
   Note: M26.N ↔ 2.6.N holds for code milestones; a security dep-bump is a code
   release. CHANGELOG (call out the CVE fix explicitly), INVARIANTS note
   (`task audit`; pins must stay CVE-clean).

## Self-review notes
- Pin `pip-audit` itself (reproducible scans) but expect its *vuln database* to
  update over time — that's the point; the tool is pinned, the advisories aren't.
- `--no-deps` scans exactly our pinned set (we don't have a hashed lockfile);
  fine for an app. A future tightening is `pip-compile --generate-hashes`.
- The multipart bump is the substance here — verify form handling still works;
  don't ship the scanner while leaving the known hole open.
- Ordering: independent of git/coverage/pre-commit; can run any time. If it runs
  before M26.24, it's the version bump; if after, adjust the number to stay
  monotonic.

## Out of scope
- `npm audit` for the JS devDeps (low value — they're dev-only, not shipped);
  note as a possible future add.
- SBOM generation, license scanning.
