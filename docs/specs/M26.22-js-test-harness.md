# M26.22 — JS test harness for the web UI — SPEC

**Status: specced, awaiting go-ahead. Largest effort of the tooling set; do last.
Do NOT implement without explicit approval.**

## Why

`static/js/chat.js` and `static/js/voice.js` are the biggest **untested** surface.
Today they're only checked by *source-structure* assertions in
`test_chat_status_ui.py` / `test_ui_correctness.py` (grep for a `try/finally`, a
`typeof` guard, etc.) — no JS actually runs in the suite. M26.10 explicitly
deferred a real harness to "Later / unscheduled" and verified that milestone by
hand with Playwright. That means UI regressions (the exact class M26.10 fixed —
failed-answer replay, error-scope leaks, panel-load races) can only be caught by
manual browser testing. A weak agent won't do that reliably.

This is the one tooling item that adds a **new toolchain (Node)** to a
Python-only repo, which is why it's ranked last and kept optional.

## Design decision to make at implementation

**Node toolchain vs. staying Python.** Two viable paths — pick one with the user:
- **(A) vitest + jsdom** (recommended if UI test depth is wanted): real DOM,
  fast, good assertions. Cost: `package.json`, `node_modules`, a JS test dir, and
  Node in CI (M26.20 would gain a second job). Best long-term.
- **(B) Playwright against the running app** (Python — `pytest-playwright`):
  no Node/JS-tooling footprint, reuses the existing Python suite, exercises the
  *real* app end-to-end. Cost: slower, heavier (browser download — note the
  sandbox already has Chromium at `/opt/pw-browsers`), flakier; needs a running
  server fixture. Best if we want E2E over unit-level JS.

The two solve different problems (B is integration/E2E; A is fast unit tests of
JS logic). If the goal is "catch the M26.10 class of bug cheaply," **A** is the
better fit; if it's "prove the whole page works," **B**. Interview the user.

## Scope (path A — vitest + jsdom)

1. `package.json` (dev-only: `vitest`, `jsdom`, `@vitest/*`), `.gitignore`
   `node_modules/`, a `vitest.config.js` with `environment: "jsdom"`.
2. **Refactor `chat.js` for testability** — currently it's an IIFE/DOM-coupled
   script. Extract the pure logic (turn assembly, success-branch gating,
   error-scope handling, panel-load-token guard) into functions that accept
   dependencies (fetch, DOM nodes) so they can be unit-tested without a live
   server. Keep a thin DOM-wiring shim. **This refactor is the real work and the
   real risk** — do it in narrow steps with the source-structure tests still
   passing as a guard, then add JS unit tests that assert the M26.10 behaviours
   directly (failed answer not replayed; single "Network error"; voice absent →
   UI survives; canonical provider selectable on `/providers` 500).
3. **Taskfile:** `test:js` task (`npx vitest run`). Keep it *separate* from
   `task test:run` (Python) so Python-only contributors aren't forced to install
   Node; document both.
4. **CI (if M26.20 shipped):** add a second job `test-js` (`actions/setup-node`
   → `npm ci` → `npx vitest run`). Independent of the Python job.
5. **Docs:** `docs/TESTING.md` gains a "Frontend tests" section; INVARIANTS notes
   that the source-structure guards stay (belt-and-suspenders) alongside the new
   runtime tests. Update the M26.10 "JS runtime not exercised" caveats to point
   at the new harness.
6. **Version:** if `chat.js`/`voice.js` are refactored (behaviour must be
   identical — verify with Playwright smoke as M26.10 did), bump patch; if purely
   additive test scaffolding, docs-like. Judgement at implementation.

## Self-review notes
- The refactor must be **behaviour-preserving**; re-run the M26.10 Playwright
  smoke (headless Chromium at `/opt/pw-browsers`) before/after and diff behaviour,
  since the Python suite can't see JS regressions.
- Do NOT let the harness delete the existing source-structure tests — they're
  cheap and catch "someone rewrote the file" even if a JS test is missing.
- Keep Node strictly dev/CI — it must never become a runtime dependency of the
  app (which is Python/Docker).

## Out of scope
- Visual-regression / screenshot testing.
- Rewriting the vanilla-JS UI into a framework (explicitly a non-goal per the
  roadmap).
