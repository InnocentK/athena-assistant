# M28.2 — Claude-CLI token usage (JSON envelope) — SPEC

**Status: approved (overnight batch, pre-approved by user). → 2.8.2.**
The deferred M27.1 follow-up: capture token usage from the Claude CLI so the
primary provider stops reporting "Tokens: unavailable".

## The constraint that shapes the design

This is developed in an environment that **cannot run the real `claude` CLI**
(no network in the device VM; binary lives on the macOS host). So the design
must be safe under envelope uncertainty: **any deviation from the expected JSON
shape degrades to today's behavior** — never break a working provider for a
metric (the M27.1 principle).

## Design

1. **Feature-detect, don't assume.** `_supports_json_output()`: run
   `claude --help` (10s timeout, same subprocess hardening) once per adapter
   instance (cached); True iff `--output-format` appears in its stdout+stderr.
   Any exception → False. No help support → today's plain invocation, verbatim.
2. **JSON path.** When supported, invoke
   `claude -p <prompt> --output-format json`. On exit 0, `json.loads(stdout)`:
   - content: the `"result"` key (expected envelope:
     `{"type":"result","result":"...","usage":{"input_tokens":N,"output_tokens":N,...}}`).
   - usage: map `input_tokens`→`prompt_tokens`, `output_tokens`→
     `completion_tokens`, total = sum when both present; ints only (reject
     bools), any missing piece just omitted → `metadata["usage"]` exactly like
     the API adapters, so the router/UI/CLI surfaces light up unchanged.
   - **Fallbacks:** stdout not JSON, or no `"result"` key → use raw stdout as
     the answer (success), usage omitted. JSON has `"is_error": true` → treat as
     provider failure with the result text as error.
3. **Failure path unchanged.** Non-zero exit / timeout / spawn error behave
   exactly as today (error strings preserved for the M22 error-kind
   classification).
4. **Subprocess hardening kept** (INVARIANTS): arg-list, `stdin=DEVNULL`,
   `encoding="utf-8", errors="replace"`, timeouts — help probe included.
5. **Morning validation for the user** (documented in CHANGELOG + report):
   run `claude -p "Say hi" --output-format json` and eyeball that the envelope
   has `result` + `usage.input_tokens`/`output_tokens`; if it differs, the
   fallback means Athena still answers correctly — file the envelope so the
   parser can be adjusted.

## Tests (all mocked subprocess.run)
- help advertises the flag → invocation includes `--output-format json`;
  envelope parsed → content + mapped usage on `metadata["usage"]`.
- help lacks the flag → plain invocation (no flag), no usage, behavior identical
  to today; help probe result is cached (one help call across two completes).
- JSON mode, exit 0, non-JSON stdout → success with raw stdout, no usage.
- JSON mode, valid JSON, no `result` → raw stdout fallback.
- `is_error: true` → success=False with error text.
- usage partial / bool-polluted → only valid ints mapped.
- non-zero exit → error path unchanged; help probe failure (exception) → plain.

## Out of scope
- Streaming envelopes (`--output-format stream-json`) — M30 territory.
- Cost fields (`total_cost_usd`) — pricing stays out (M27.1 decision).
- Other CLI adapters (gemini/grok/hermes) — still "unavailable"; separate work
  if their CLIs grow usage output.

## Self-review
- Double-subprocess cost: the help probe runs once per adapter lifetime (~ms,
  local, no network) — acceptable; caching prevents per-request cost.
- Worst regression case: CLI honors the flag but emits an unexpected envelope →
  user sees raw JSON as the answer. Mitigated by `result`-key fallback to raw
  stdout (the raw text IS the envelope only when the CLI really is JSON-mode,
  in which case the envelope parse almost certainly succeeded). Accepted risk,
  flagged for morning validation.
- Version: code change to the primary provider → **2.8.2**.
