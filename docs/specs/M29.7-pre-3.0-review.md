# M29.7 — pre-3.0 review & docs sweep — SPEC

**Status: APPROVED by user (with the Part 4 addition). Docs/quality only —
no version bump (app stays 2.9.6). Code fixes that the review identifies are
NOT made here — they become M29.8+ micro-milestones.**

## Why

Between 2.8.1 and 2.9.6, **fourteen milestones landed in roughly two working
days** (M28.2–M28.6, M29.0–M29.6, plus the M30 spec), most written in one
overnight autonomous run. Every one passed the full gate, but this project's
history is explicit about what gates don't catch: the M26.18 router split
shipped green with 438 tests passing and still carried a real bug that only a
fresh-eyes review found. Before a major release, the code written at speed
gets read again at leisure. This is that milestone.

## Part 1 — the review

### Targets, by intensity

**Primary (full fresh-eyes read, every lens):** the fast-batch code —
`providers/claude.py` (JSON envelope path, M28.2/M29.5), `core/config.py`
(resolution order, M28.5), `app/routers/core.py` (profiles endpoints + /chat
history integration), `cli/doctor.py`, `core/chat_turn.py`,
`history/manager.py`, `app/routers/history.py`, `cli/repl.py`,
`cli/history_cmd.py`, the M29.3 upload block in `app/routers/files.py`, and
the M29-era edits to `static/js/chat.js` (conversation threading, past-
conversations restore, attach flow).

**Secondary (targeted spot-check, security + contract lenses only):** the
pre-batch feature code that shipped with dedicated tests and more deliberate
pacing — PWA (M26.28), live status + token usage (M27.x), portable profiles
(M28.0/1), mobile CSS (M28.4). Focus: attack surfaces and cross-feature
interactions (e.g. portable export vs the new `history/` dir; service worker
vs the new endpoints).

### Lenses (each applied as its own pass, findings recorded per lens)

1. **Correctness** — module-by-module read against its spec; special
   attention to edge/error paths the mocked tests may mirror rather than
   verify.
2. **Security** — traversal surfaces (upload names, conversation ids,
   profile names — each claims regex-before-path; verify no bypass),
   secret hygiene (doctor output, leak scan, envelope fixtures), destructive
   endpoints' guards (delete/activate/import), subprocess hardening on the
   new `claude --help` probe, resource abuse (upload cap enforcement,
   unbounded history growth characteristics).
3. **Concurrency** — the ConversationStore lock discipline (append from
   `to_thread` workers vs list/read; no lock held across `read()` recursion),
   profile-switch re-pointing vs in-flight requests, REPL single-thread
   assumptions, uploads under concurrent same-name writes.
4. **Cross-surface consistency** — the contracts that now span three
   surfaces (web, one-shot CLI, REPL): stdout/stderr rules, success-only
   replay, conversation threading, usage/status lines. Divergences are
   findings even when each surface is individually "correct."
5. **Test quality** — do the new tests assert behavior or echo the
   implementation; anything tautological; the gaps behind the per-module
   coverage numbers (repl.py is the lowest of the new modules at 77% —
   examine what the uncovered 23% is).
6. **Agent ergonomics** — INVARIANTS completeness for everything a future
   agent could plausibly break; naming-convention adherence; whether each
   new package's `__init__` says what it owns.

### Pre-identified findings (verified during spec investigation — the review
must disposition these along with whatever else it finds)

- **(a) Upload filename race** (`app/routers/files.py`): `_unique_path`
  checks existence, then the file opens with `"wb"` — two concurrent
  same-name uploads can both pass the check and the second silently
  overwrites the first. Single-user severity is low; `open(…, "xb")` with a
  retry loop is a five-line fix. Expected bucket: **fix (M29.8)** — it
  contradicts the endpoint's own "never overwrite" contract.
- **(b) Orphan-user-turn inconsistency across surfaces**: on a failed
  provider turn, the **web UI keeps** the user's question in replayed
  context (pushed before the fetch), the **REPL drops it** (history appended
  only after the success check), and **restore/`/resume` keep it** (only
  failed *assistant* turns are filtered). Three surfaces, two semantics.
  M26.10's actual rule was "never replay the *failure text*" — it is silent
  on the orphaned question. The review decides the intended semantics
  (recommendation to be argued in the report: keep the user turn everywhere —
  the user did ask it — i.e. align the REPL to the other two) and the
  alignment fix goes to **M29.8**.
- **(c) Same-second conversation-id ordering tie** (deferred item 1, per
  discussion): two conversations created in the same second sort by random
  suffix in every newest-first listing. Investigate whether any surface
  makes a *decision* (not just a display) based on ordering; assess the two
  candidate fixes (sub-second id stamps vs sorting listings by first-turn
  timestamp — the latter changes no id format). Bucket per the findings:
  fix in M29.8 if consequential, else **defer with a Later/unscheduled
  entry** (explicitly NOT silently accepted — per user direction).

### Finding disposal — the three-bucket rule (every finding exits through
exactly one door; "noted in the report" is not a door)

1. **Fix now** → a scoped M29.8+ micro-milestone (listed in the report with
   suggested ordering; implemented only after user approval).
2. **Defer** → an actionable entry with a trigger condition added to
   CLAUDE.md's Later/unscheduled **as part of this milestone**.
3. **Bless as designed** → an INVARIANTS (or appropriate doc) note stating
   the behavior is intentional, added as part of this milestone.

### Deliverable
`docs/history/REVIEW-3.0-2026-07.md` (naming follows REVIEW-2026-07.md):
scope, method, per-lens findings each tagged with its bucket and its
destination (milestone number / CLAUDE.md entry / INVARIANTS section), plus
the proposed M29.8+ queue for user approval.

## Part 3 — coverage floor

Measured now (536 tests): **source-only coverage is 76.86%**, floor is 70
(set when reality was 74). Every new module: chat_turn 86%, history/manager
95%, claude 94%, doctor 87%, history_cmd 86%, config 92%, repl 77%. Proposal:
**raise `fail_under` to 74** — same ~3-point headroom philosophy as the
original setting (70 under 74), ratcheting the guarantee without making
honest DAV-mock refactors trip CI. Config-only change (`pyproject.toml`),
no-bump precedent from M26.24.

## Part 4 — codify the review cadence (user-requested addition)

Write a standing **review-cadence rule** into CLAUDE.md's milestone-loop
section so future agents run reviews like this one without being told.
Triggers (whichever fires first), chosen to track *unreviewed change volume*
rather than version arithmetic (minor versions here are epics of very
different sizes — a per-N-versions rule would measure the wrong thing):

1. **Before any major version bump (X.0.0)** — a FULL review (all six
   lenses, docs sweep, coverage re-measure) is a mandatory release gate.
2. **At each epic close** (end of a minor series, before the next epic
   starts) — a scoped fresh-eyes review of that epic's code: correctness,
   security, and cross-surface consistency lenses at minimum.
3. **After any autonomous batch of ≥5 milestones** (overnight runs, large
   pre-approved batches) — the batch's output gets the scoped review before
   new feature work begins, regardless of where the epic stands.

Every review: findings exit through the three buckets (fix milestone /
Later-unscheduled entry / INVARIANTS bless), report archived in
`docs/history/`, and a lens that finds nothing states what it checked.

## Self-review of this spec
- The review deliberately reads code, not diffs — the M26.18 bug lived in
  code every diff of which looked mechanical.
- Risk: review fatigue producing rubber-stamp findings. Mitigation: the
  three pre-identified findings give each lens a known-real anchor; a lens
  that finds nothing must say what it checked, not just "OK".
- Risk: docs sweep scope creep into rewriting docs wholesale. Mitigation:
  the sweep list above is closed; anything else found goes into the report
  as a finding, not into this milestone's edits.
- The M29.8 queue is proposed, not implemented — the user approves it from
  the report, preserving the loop.
