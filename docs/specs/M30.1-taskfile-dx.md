# M30.1 — Taskfile developer experience — SPEC

**Status: approved (user, 2026-07-16), implemented. Tooling/docs only — NO
version bump; the app stays 3.0.0.**

## Motivation (a real incident)

After 3.0.0 shipped, the user's `athena --provider claude "hello"` failed with
`No module named 'diagnostics'`. Root cause: their venv had
`pip install -r requirements.txt` but no (current) `pip install -e .` — the
editable install is what provides the `athena` command and maps Athena's own
packages, and NOTHING in the Taskfile ran it outside of `task ci` (buried
mid-gate). `task setup` produced an environment where `athena` doesn't exist;
`task install` refreshed deps but never the package mapping, so a venv
installed before a milestone that ADDS a top-level package breaks exactly this
way. The Taskfile almost prevented the incident; this milestone closes the gap.

## Scope

`Taskfile.yml` + docs. No Python, no JS, no behavior change to the app.

1. **`task setup`** additionally runs `pip install -e .` — first-time setup
   ends with a working `athena` command.
2. **`task install`** becomes "make the venv current": requirements **plus**
   `-e .`, with a description that says when to run it (after pulling changes).
3. **`task update`** (new) — the post-pull one-shot: `install` + `npm install`
   when npm is present (guarded skip-with-notice otherwise — Python-only
   contributors need no Node), then prints the installed version.
4. **`task doctor`** (new) — wraps the M28.6 preflight (`python -m cli
   --doctor`) so it is discoverable in `task --list` exactly when someone's
   environment is confused.

Docs: `docs/TASKFILE.md` (new/changed rows; ALSO backfills the drift found
during this milestone — the M26.19–M26.26 quality-gate and operations tasks
were never documented there), README quick start (manual path now includes
`pip install -e .`; task path mentioned), `docs/TROUBLESHOOTING.md` (the
existing `No module named 'diagnostics'` entry gains the real-world cause —
stale/absent editable install — and the `task install` remedy).

Deliberately NOT added: a `task cli --` passthrough (once installed, `athena`
IS the interface); no change to `task ci`'s own `-e .` line (the CI gate stays
self-contained).

## Self-review / risks

- `task: install` composition runs in Task's own process — no venv-activation
  assumption beyond what every existing task already makes ({{.PIP}} points
  into `.venv`).
- `update`'s npm guard is POSIX shell → `platforms: [linux, darwin]`, matching
  `setup`/`clean` precedent (Windows guidance in TASKFILE.md notes is
  unchanged).
- `doctor` propagates the CLI's exit code (1 iff a check fails) — correct for
  scripting, mildly surprising interactively; the desc says so.
- No tests change: the Taskfile is not exercised by the suite (no `task`
  binary in CI); YAML validity is checked at implementation time.

## Follow-ups surfaced by the same incident (separate milestones, proposed)

- **M30.2** — `mypy .` exits 1 on a fresh 3.0.0 checkout (8 pre-existing
  `"object" not callable`-class errors in caldav/ics modules, reproduced on
  two machines with identical pins) → `task ci`'s mypy step is red. Needs
  root-cause + fix (likely per-line ignores, pre-blessed by the pyproject
  mypy philosophy).
- **M30.3** — CLI provider adapters inherit the caller's cwd, so `athena` run
  from inside a project directory leaks that project's agent context (e.g.
  claude-code CLAUDE.md + SessionStart hooks) into chat answers. Proposal:
  run adapter subprocesses from a neutral cwd.
