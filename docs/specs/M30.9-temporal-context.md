# M30.9 — Temporal context in the system prompt — SPEC (→ 3.0.8)

**Status: approved (user, 2026-07-17 Pt 2 triage), implemented.**

## Finding

"What time is it in Chicago?" → grok: "I don't have real-time clock access."
Correct and previously by-design: providers are pure LLMs (M30.7 included)
and Athena injected no wall-clock context. The user judged an assistant
should know the time; approved as a behavior change.

## Change

`core/chat_turn.system_prompt_from()` appends one line to the provider-bound
system prompt:

    Current date and time: Friday, 2026-07-17 17:45 (CDT)

- Server-local time + timezone name (the machine Athena runs on — the
  single-user deployment's home timezone by definition).
- Appended after the profile prompt with a blank line; when the profile
  prompt is empty, the temporal line IS the system prompt. **Contract
  change:** the M29.0 "empty prompt → None (no system turn)" semantic
  becomes "providers always receive at least the temporal line";
  `system_prompt_from` now returns None only if the clock itself fails
  (guarded — a broken clock must never break a chat).
- Both surfaces inherit it (shared seam). Known and accepted: the CLI
  one-shot/REPL resolves the prompt once per process, so a very long REPL
  session's timestamp goes stale — minutes-level staleness is irrelevant to
  the use case, noted in the docstring.
- Not recorded anywhere: system prompts were never part of history/exports;
  nothing changes there. Cost: ~15 tokens/turn; minor prompt-cache churn on
  API providers (minute granularity) — negligible at single-user scale.

## Tests

- Line present and formatted (`Current date and time: <Weekday>,
  YYYY-MM-DD HH:MM`), appended after a profile prompt, alone when the
  profile prompt is empty; the M29.0 semantics test updated to the new
  contract.

## Version: 3.0.8. INVARIANTS: providers section notes the injection is
provider-bound only and must never raise.
