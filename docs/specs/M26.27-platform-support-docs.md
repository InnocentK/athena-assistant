# M26.27 — platform support & limitations docs — SPEC

**Status: specced, awaiting go-ahead. DOCS ONLY — no code, no version bump.**
Do NOT implement without explicit approval.

## Why

Athena is developed and tested on **macOS** (the author's machine) and is
designed to run in Docker on modest hardware, but the repo has never stated,
in one place, *which platforms are supported, to what degree, and with what
caveats*. That gap costs in two ways: a future agent has no canonical answer to
"will this work on Windows / in a bare container / on a phone?", and the two
deployment-adjacent efforts we've queued — the out-of-tree LXC installer and the
remote-access guidance — both need a platform matrix to point at rather than each
restating the same caveats. This milestone writes that matrix down so those
efforts (and any user) can reference one source of truth.

This is the cheapest item on the roadmap and a *dependency-of-thought* for the
LXC script and the remote-access docs, so it goes first.

## Scope

1. **New doc: `docs/PLATFORMS.md`** — a "Running Athena on <platform>" support
   matrix. One row per platform with an honest support level (Tested / Expected
   good / Works with caveats / Not supported) and the specific caveats. Rows:
   - **macOS (desktop)** — *Tested.* The primary development/verification target.
     Both transports work (API-SDK + CLI adapters, given the vendor CLIs are
     installed and logged in). This is the reference experience.
   - **Linux (desktop/server)** — *Expected good.* Same POSIX assumptions as
     macOS; the CI matrix runs the suite on Linux (Python 3.10/3.11), so the
     Python side is actively exercised. CLI adapters work if the vendor CLIs are
     present. This is the recommended server platform.
   - **Windows** — *Works with caveats.* The FastAPI/UI/API-transport path is
     expected to run under a normal CPython install, but the **CLI provider
     adapters** are the weak point: they shell out to vendor CLIs as subprocesses
     with POSIX-flavoured assumptions (arg-lists, `stdin=DEVNULL`, signal/timeout
     handling, path/quoting). These are **not tested on Windows**; users wanting
     CLI transports on Windows should prefer **WSL2**, which behaves like the
     Linux row. Document this as a real limitation, not a "should be fine."
   - **Container (Docker / LXC)** — *Works, API-transport-only by default.* A
     stock container has Python + FastAPI trivially, but the **vendor CLIs are
     not present and usually need interactive login**, so a headless container is
     **API-transport-only** (chatgpt / grok-api / ollama via keys in `.env`)
     unless the operator bakes the CLIs + their auth into the image. This row is
     the canonical home for the caveat the LXC installer script depends on.
   - **Mobile (iOS / Android)** — *No native app; not a run target.* Athena is a
     server process; there is no mobile build and none is planned. Phones reach a
     desktop/server instance **remotely over Tailscale/VPN** (see remote-access
     note), using the existing browser UI. State plainly: use it *from* a phone,
     don't run it *on* one.
2. **Remote-access pointer (brief, in the same doc).** A short section restating
   the standing security posture — Athena is single-user with **no auth layer**,
   so it must never bind an untrusted interface; remote reach is the operator's
   responsibility via **Tailscale/VPN or an authenticated reverse proxy + TLS**.
   Keep it to a pointer + the one safe pattern; the fuller remote-access doc is a
   separate (later, docs-only) item. Cross-link `SECURITY.md`.
3. **Wire it into the index.** Add `PLATFORMS.md` to `docs/README.md` (the
   "Getting started / using it" or "Operating a deployment" section) so it's
   discoverable. Optionally cross-link from `INSTALLATION.md`.
4. **Version:** **no bump.** Pure documentation; the app stays at its current
   version. CHANGELOG entry under an `[Unreleased] — Milestone 26.27` heading,
   consistent with the other no-bump docs/tooling milestones.

## Self-review notes

- **Honesty over optimism.** The value of this doc is that it says what is
  *actually* tested (macOS) vs *expected* (Linux) vs *caveated* (Windows CLI
  adapters, headless-container CLI transports). Resist upgrading "expected" to
  "supported" — the whole point is to not over-promise to a future agent/user.
- **No new claims that aren't true.** Don't assert Windows works if we haven't
  run it; the row explicitly says the CLI-adapter path is untested there.
- **Single source of truth.** Once this exists, the LXC script's transport
  caveat and the remote-access doc should *link here*, not restate — that's the
  reason to build it first.
- This is docs-only, so the "gate" is really just: pre-commit hygiene clean
  (final newline, no trailing whitespace, valid Markdown), links resolve, and
  the full existing suite is unaffected (no code touched).

## Out of scope

- Any code change to improve Windows/container support (e.g. a Windows-safe
  subprocess path). This milestone *documents* the current state; changing it is
  separate future work if ever desired.
- The full remote-access how-to (Tailscale setup walkthrough, reverse-proxy
  configs) — this doc only points at the pattern.
- The LXC installer script itself (out-of-tree, separate project).
