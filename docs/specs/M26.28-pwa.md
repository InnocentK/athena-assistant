# M26.28 — installable PWA (web UI) — SPEC

**Status: specced, awaiting go-ahead. Small user-visible frontend feature →
version bump. Do NOT implement without explicit approval.**

## Why

`docs/PLATFORMS.md` (M26.27) says the way to use Athena from a phone is to reach
a server instance over Tailscale/VPN in the browser. This milestone makes that
browser experience feel like an app: an installable **Progressive Web App**
(add-to-home-screen, standalone display, app icon). It is deliberately *polish*
on top of the existing UI — no new subsystem, no app-logic change.

## The load-bearing caveat (shapes the whole design)

**Service workers and install require a *secure context* — HTTPS, or
`localhost`/`127.0.0.1`.** A plain `http://<tailscale-ip>:8000` is **not** a
secure context: the service worker silently won't register and no install prompt
appears. HTTPS over a tailnet (`tailscale serve` / a tailnet cert) or the
reverse-proxy-plus-TLS pattern provides it — and those are exactly the
remote-access setup `PLATFORMS.md` already points at. So the PWA **only fully
lights up once the TLS legwork is done**; it is polish on the deferred
remote-access path, not an escape from it. Consequences for the build:
- The service-worker registration MUST **degrade gracefully**: over plain HTTP
  (`'serviceWorker' in navigator` is false / registration rejects) the page still
  works as an ordinary browser tab. No errors, no broken UI.
- The docs (`PLATFORMS.md` mobile row + this milestone's notes) state the
  secure-context dependency plainly so nobody expects install to work over
  bare HTTP.

## Scope

1. **Web app manifest** — `static/manifest.webmanifest` with the minimum useful
   set: `name`/`short_name` (from the assistant name is nice-to-have but the
   static file can't read the profile — use "Athena", acceptable), `start_url:
   "/"`, `scope: "/"`, `display: "standalone"`, `background_color`,
   `theme_color` (match the UI header), and `icons`. Referenced from the template
   via `<link rel="manifest">`.
2. **Icons** — generated PNGs under `static/icons/`: `icon-192.png`,
   `icon-512.png`, a **maskable** `icon-maskable-512.png` (with safe-zone
   padding), and `apple-touch-icon.png` (180×180, for iOS which ignores the
   manifest icons for the home-screen glyph). Generated once (Pillow, a
   build-time-only tool — NOT a runtime dep) and committed as binary assets.
3. **Service worker** — `static/js/sw.js`, served at **`/sw.js`** (root path, so
   its scope is `/` and it controls the whole app) via a small route that injects
   the app version into the cache name. Behaviour:
   - **Cache only the static shell** (CSS/JS/icons/manifest) + the root
     navigation, via runtime caching. **Never cache dynamic/API responses**
     (`/chat`, memory, settings, DAV, backup, …) — Athena is server-dependent;
     pretending to work offline would be a correctness bug. Non-GET and
     non-static requests bypass the SW entirely.
   - **Cache name is versioned with `app.version`** (injected by the route) so a
     release drops the old shell cache on `activate` — same anti-stale-asset
     discipline as the M26.1 `?v=` cache-busting (INVARIANTS "UI correctness").
   - `skipWaiting` + `clients.claim` so an updated SW takes over promptly.
4. **Registration** — a tiny `static/js/pwa.js` (loaded from the template) that
   registers `/sw.js` **inside `if ('serviceWorker' in navigator)`** and swallows
   registration errors. This is the graceful-degradation guard.
5. **Template tags** — in `templates/index.html` `<head>`: `<link rel="manifest">`,
   `<meta name="theme-color">`, `<link rel="apple-touch-icon">`, the iOS
   standalone metas (`apple-mobile-web-app-capable`,
   `apple-mobile-web-app-status-bar-style`, `mobile-web-app-capable`), and the
   `pwa.js` script tag (versioned `?v=` like the others).
6. **The one route** — `GET /sw.js` (colocated with the `GET /` index route in
   `main.py`, since both serve the browser-UI shell): reads `static/js/sw.js`,
   substitutes the version, returns `application/javascript`. Manifest and icons
   need no route — they're plain static assets under `/static`.
7. **Tests:**
   - **Python** (`tests/test_pwa.py`): `GET /sw.js` → 200, `content-type`
     `application/javascript`, body carries the current version in the cache
     name; `GET /static/manifest.webmanifest` → 200 with `display: standalone`
     and `start_url: "/"`; the shell icons are served.
   - **JS** (`tests/js/pwa.test.js`, jsdom via the M26.22 harness): with no
     `navigator.serviceWorker`, running the registration is a no-op (no throw);
     with a mocked `register`, it's called with `/sw.js`.
8. **Version:** user-visible UI feature → **bump to 2.6.28** (`core/version.py`).
   CHANGELOG + `docs/TESTING.md` (new tests) + a cross-link from the
   `PLATFORMS.md` mobile row. INVARIANTS note (SW caches shell only, never
   dynamic; cache name is version-scoped).

## Self-review notes

- **jsdom can't run a real service worker** — so the JS test targets the
  *registration guard* (the degradation contract), and the SW's cache logic is
  covered by keeping it small and by the Python route test. Don't try to
  unit-test the SW fetch handler in jsdom; that's not what the harness is for.
- **Don't over-reach the manifest** — no push notifications, no background sync,
  no share_target. Name, icons, display, colors. Those are the parts that make
  "install" work; the rest is scope creep.
- **The SW must never make the app seem to work offline when it can't.** Caching
  the shell is fine (fast loads, standalone launch); caching a chat turn is not.
  The fetch handler's allowlist (static + navigation only) is the guard — treat
  it like the striplist in M28: build from an allow set, not a deny set.
- **Secure-context degradation is the correctness bar**, mirroring M27.1's
  "unavailable" honesty: on bare HTTP the feature is simply absent, cleanly.

## Out of scope
- Offline chat / queued sends / background sync.
- Push notifications, web-share target, file-handling API.
- Any change to the remote-access/TLS setup itself (that's the user's
  Tailscale/proxy config; this milestone only *documents* the dependency).
- Per-profile manifest naming (the static manifest uses "Athena").
