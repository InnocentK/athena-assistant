# M31.4 — Save destinations + derived filenames — SPEC (→ 3.1.4)

**Status: approved (user, 2026-07-19, hybrid chosen: "data/saved AND
download to my device… user enable which one or both in settings").
Refines M31.3 within hours of shipping — probe iteration working as
intended.**

## Problems (user review of M31.3)

1. `reply-<timestamp>.md` discards the obvious name — the reply itself said
   `Ganymede_Notes.md`.
2. `data/uploads/` semantically holds what the USER sent in; assistant
   output landing there muddies the Files tab.
3. And the user's real-world want was hybrid: a copy on the server (to
   re-attach/browse later) AND/OR a copy on the device in hand, chosen in
   Settings.

## Changes

**Derived filenames (both destinations).** `_replyFilename(text)`: first
markdown heading → slug (`Notes-on-Ganymede.md`); else first ~6 words of
the first line → slug; slug shorter than 3 chars → the old
`reply-<timestamp>` fallback. Sanitized to the upload charset client-side,
re-sanitized server-side, unique-suffixed on collision as always.
Deliberately dumb — no model-suggested-name parsing.

**Server destination `data/saved/`.** `POST /files/upload` gains an
optional multipart field `dest` ∈ {`uploads`, `saved`} (default `uploads`
— the attach flow is untouched). Unknown dest → 400 before any write. Same
envelope end-to-end: sanitize, exclusive-create `xb` suffix loop, 10 MB
streamed cap, `mkdir` on demand. STILL the one browser-reachable write
path — a fixed two-entry enum, not a client-controlled path. `data/` is
already wholesale-allowlisted (read/search) and gitignored, so Files-tab
preview, attachment inlining, and repo hygiene need no config change; the
Files tab adds a best-effort `saved/*` merge beside `uploads/*`.

**Device download.** Client-side only: Blob → object URL → anchor
`download` click (on iOS this lands in the share/Files flow). No server
involvement, nothing recorded.

**Settings — new "Saving replies" section** (browser-local, instant-apply,
`athena-save-prefs` in localStorage with the M30.6 private-mode memory
fallback): "Save to server (data/saved)" **default ON** (preserves M31.3
behavior) and "Save to this device (download)" **default OFF**. The Save
button reads prefs at CLICK time and performs every enabled action; with
both off, new replies render no button at all. Feedback: "Saved ✓" with
the outcome list in the tooltip; a server failure shows "Save failed" and
re-enables (a device copy may already have downloaded — retry re-downloads,
accepted).

## Tests

- Python (`test_files_api.py`): `dest=saved` writes under `data/saved/`
  and reports that path; bogus dest → 400, nothing written; default stays
  `data/uploads/` (existing M29.3 suite unchanged).
- jsdom (`saveReply.test.js` reworked): heading-derived and first-words
  filenames + timestamp fallback (via `_replyFilename` unit calls);
  server-pref save posts `dest=saved`; device-only downloads (object-URL
  spy) with zero upload POSTs; both-on does both; both-off renders no
  button; failure/exclusion cases kept from M31.3.
- Pins: `_replySaveButton(` stays 3; `_replyFilename(` = 2 (definition +
  the one call); the dest literal `("dest", "saved")`; the prefs key.

## Self-review / risks

- The dest enum is the guarded edge: it must never become a free-form
  path. Server-side membership check before any filesystem touch.
- Old bubbles rendered before a settings change keep their buttons but act
  on CLICK-TIME prefs — the same instant-apply semantics as voice prefs.
- iOS download UX varies by browser (sheet vs silent save) — user-verified
  live, not simulated.
